COLLABORATION RULES (ENFORCED)
──────────────────────────────────────────────────────────────────────────────

✓ ALLOWED:
  • Exactly 1 primary specialist per request
  • Primary may invoke AT MOST 1 peer
  • Peer invocation is single-hop only
  • Primary owns final integrated output
  • Fallback chain pre-computed at routing time
  • Context Planner as valid peer (any primary)
  • Code Reviewer as valid peer (any primary)

✗ NOT ALLOWED:
  • Chains (A → B → C)
  • Circular dependencies (A → B → A)
  • Multiple simultaneous peers
  • Peer invoking another peer
  • SRE making file edits (use Impl Guardian)
  • Bypassing verification gate

PEER COLLABORATION EXAMPLE: Implementation Guardian → Senior Backend
──────────────────────────────────────────────────────────────────────

Step 1: Router selects Implementation Guardian (highest score)
        Task: "Implement new feature using a new backend API"

Step 2: Implementation Guardian starts: "I'll build the frontend component"
        Issue discovered: "Need API contract first"

Step 3: Implementation Guardian invokes peer: Senior Backend
        Request: "Define API contract for [feature]"

Step 4: Senior Backend returns:
        • OpenAPI spec
        • Request/response schemas
        • Security requirements
        • Error codes

Step 5: Implementation Guardian integrates:
        • Builds component using API spec
        • Adds tests
        • Adds error handling

Step 6: Verification gate runs:
        • Security checks pass
        • Contract validation passes
        • Tests pass

Step 7: Response returned:
        • Implementation Guardian output (component)
        • Senior Backend output (API spec)
        • Consolidated trace showing peer invocation


MEMORY & TOKEN TRACKING
──────────────────────────────────────────────────────────────────────────────

Router maintains in .ai/memory/active-work.md:
  • Specialist selection history
  • Routing scores (debug trace)
  • Peer invocation patterns
  • Fallback activation frequency
  • Token usage by specialist
  • Latency metrics by tier

Monitor for:
  • Fallback chain activation (indicates suboptimal routing)
  • Peer invocation frequency (indicates cross-domain work)
  • Token budget overruns (indicates tier mismatch)
  • Latency budget violations (indicates load issues)


SUPPORT & TROUBLESHOOTING
──────────────────────────────────────────────────────────────────────────────

Q: "My request routed to the wrong specialist"
A: Router uses deterministic scoring. Check:
   1. Domain description clear in request?
   2. Risk level stated explicitly?
   3. Budget tier adequate for task?

Q: "Fallback chain activated too often"
A: Indicates routing suboptimal. Check active-work.md for patterns.

Q: "Token budget exceeded"
A: Peer invocation or multiple fallbacks used. Check task scope.

Q: "I need cross-domain expertise"
A: Use Implementation Guardian primary, which can invoke 1 peer specialist.

Q: "Can I skip verification gate?"
A: No. Verification gate is mandatory for security/contract/test validation.
